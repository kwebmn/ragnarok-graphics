# Окна вещей через пакеты: дизайн

Статус: одобрено владельцем 25.11.2026 («да»).

## Зачем

Владелец: «у нас есть глюки с интерфейсом, особенно с покупкой, передачей вещей… надо подумать, возможно
спроектировать общий подход и избавится от этих глюков». С середины октября было 99 исправлений, 22 из них — про
перенос вещей. Причина общая. Наши окна вещей — второй слой поверх спрятанных окон игры. Данные они читают из памяти
игры, а действия выполняют через её окна: имитируют перетаскивание, шлют сообщения её окнам. У каждой операции два
хозяина. Отсюда потерянные и двойные клики, рассинхрон и клики, ушедшие не туда (3.0.23-beta.15: вывески на улице
забирали клики у «Складу»).

Решение владельца:
1. На время переделки окна вещей выключены у всех. Сделано в 3.0.24-beta.1, там же окна игры отодвигаются с наших
   панелей.
2. Переделка по варианту 2: наш слой сам отправляет серверу пакеты действий и сам ведёт состояние вещей по ответам
   сервера.

## Цели

- У действия с вещью один хозяин — наш слой. Он отправляет пакет и узнаёт исход из ответа сервера.
- Окно показывает то, что сказал сервер, а не то, что успела записать в память игра.
- Одно нажатие — одно действие. Повтор, пока ждём ответа, не отправляет второй пакет.
- Если сервер отказал, окно говорит почему: склад полон, перевес, не хватает зени.
- Окна переделываются по одному. Каждое включается обратно, только когда его проверили в игре.

## Не цели

- Новый вид окон и удобство для новичков. Это отдельный разговор, когда механика станет надёжной.
- Сервер uAthena не меняем.
- Не заменяем игру целиком. Игра продолжает получать все пакеты сервера и обновлять своё состояние: от него зависят
  вес, хотбар и её собственные окна.

## Чего нельзя допустить

- Потерять или удвоить вещь из-за нашего пакета.
- Отправить пакет, когда поток сервера не понят: после разрыва, на чужом сокете, во время смены карты.
- Снова получить двух хозяев: родное окно игры и наше одновременно действуют над одним и тем же.

## Ограничения

- Клиент — kRO Sakexe 2007-05-07, PACKETVER 7, номера пакетов перемешаны. Номер и длина каждого пакета берутся из
  `/root/uAthena/db/packet_db.txt` для этой даты клиента и сверяются с тем, что отправляет сама игра (журнал её
  отправок в первой бете).
- Отправка и разбор потока уже есть в сессии пада (`src/pad/core/session`: `request()`, `onServerData()`,
  разбивка потока на пакеты, «поток понят»). Сейчас она работает только при `[pad] enabled`. Слою вещей она нужна
  всегда.
- Всё на потоке игры, как остальные окна.

## Подходы

1. **Пакеты отправляем сами, данные читаем из памяти игры.** Быстрее всего. Остаётся вторая копия правды: память
   игры может отставать от сервера.
2. **Пакеты отправляем сами, состояние ведём по пакетам сервера.** У окна один источник — сервер. Нужно разобрать
   пакеты списков вещей. **Выбран владельцем.**
3. **Не трогать механику, переделать только вид.** Отброшен: глюки идут от управления чужими окнами.

## Как устроено

### 1. Сеть всегда включена

Сессия (разбор потока сервера и отправка) работает при любом `[pad] enabled`. Пад лишь добавляет к ней своё
управление. Отправка возможна, только когда сессия считает поток понятым. Иначе действие отклоняется с записью в
журнал, и окно говорит «зачекайте».

### 2. Состояние вещей — `core/item_state`

Четыре хранилища: сумка, склад, телега, обмен. Предмет хранится по серверному индексу: номер предмета, количество,
опознан ли, заточка, четыре карты, атрибут, место надевания. Состояние строится только из пакетов сервера: полные
списки, добавление, удаление, изменение количества, закрытие склада или обмена. Чистое ядро без Windows, тесты на
записанных потоках байтов.

### 3. Действия — `core/item_actions`

Типизированные запросы превращаются в байты по таблице версии:
- в склад и из склада, закрыть склад;
- в телегу и из телеги, склад ↔ телега;
- купить и продать у NPC;
- купить в лавке;
- обмен: положить, подтвердить, совершить.

У каждого отправленного действия есть ожидание: какой ответ сервера его закрывает и тайм-аут 2 с. Пока действие над
ячейкой ждёт ответа, второе для неё не отправляется. Ответ меняет состояние, оптимистичных правок нет. Отказ
сервера превращается в слова для окна.

### 4. Окна

Окно читает только `item_state` и отправляет только `item_actions`. Окно игры для той же вещи остаётся закрытым и
спрятанным, как сейчас: сервер открывает его своим пакетом, игра его создаёт, мы его прячем и не трогаем. Отрисовка
нынешних окон сохраняется, меняется только то, откуда они берут данные и как действуют.

### 5. Порядок

1. Сеть всегда включена, `item_state` для сумки и склада, журнал отправок самой игры (сверка номеров).
2. «Склад»: положить, забрать, закрыть. Включить у тестеров.
3. «Візок».
4. «Магазин» NPC: купить, продать.
5. «Лавка»: купить.
6. «Обмін».
7. «Речі»: использовать, надеть, выбросить. Последней, потому что от неё зависят хотбар и панели.

Каждое окно после проверки в игре возвращается включённым по умолчанию — только по слову владельца.

### 6. Проверка

- Тесты ядра на записанных потоках: список, добавление, отказ, тайм-аут, повторное нажатие.
- В журнале на каждое действие строка: что отправлено, каким ответом закрыто, за сколько миллисекунд.
- Отчёт об ошибке несёт последние 50 действий.

## Решения за исполнителем

- Точные номера и длины пакетов (из packet_db и журнала самой игры).
- Как именно сессия становится общей: вынести из пада или включать без управления падом.
- Вид состояния «ждём ответа» на ячейке: в стиле текущих окон.

## Решено

- Готовое окно сначала включается тестерам (в бете, по галке), всем — после их проверки и слова владельца.
