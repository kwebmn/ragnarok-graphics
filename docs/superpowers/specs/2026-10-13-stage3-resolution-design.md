# uaRO Graphics — этап 3: высокое разрешение и масштаб интерфейса (уточнение спецификации)

Основание: спецификация v1 `2026-10-13-uaro-graphics-design.md` (§4.2, §4.3, §6, §9 п. 3). Этап 1 (0.2.0) принят
пользователем: «разницы по сравнению со старым не почувствовал». Этот документ уточняет §4.2 и §4.3 для этапа 3 и в
местах расхождений заменяет их.

## 1. Цель

Установка пользователя: монитор 4K (3840×2160), масштаб Windows 175 %, игра в окне 1920×1080 (ROExt). Игра не умеет
работать с масштабом Windows, поэтому Windows растягивает её окно до 3360×1890 точек экрана, и картинка мягкая
(с dgVoodoo — так же).

После этапа 3:
- окно и интерфейс того же размера, что сейчас; мир (земля, здания, модели, края трёхмерного) рисуется в настоящих
  точках окна — у пользователя 3360×1890 вместо растянутых 1920×1080;
- игра, ROExt и uaRO Pad ничего не замечают: то же окно, те же координаты, та же мышь;
- при масштабе Windows 100 % и игре в окне всё как в 0.2.0 (кроме суперсэмплинга, если он включён);
- игра на полный экран (окно без рамки на весь монитор): масштаб = монитор / разрешение игры (1920×1080 на 4K → 2).

## 2. Факты: эксперимент DPI (Windows 11, сборка 26200, масштаб 175 %)

Программа `spikes/dpi-test` (32 бита, без манифеста — как `uaRO.exe`) показала один узор из линий толщиной в одну
точку тремя способами, сняла своё окно с экрана и посчитала серые точки (их не бывает, если кадр выведен точка в точку):

| Вариант | Серых точек | Красная рамка 3 точки | Итог |
|---|---|---|---|
| 1. Буфер swap chain размера окна для Windows (960×540) — как в 0.2.0 | 71 % | 5 точек | растянуто |
| 2. Буфер в настоящих точках окна (1680×945) на том же окне | 0 % | 3 точки | точка в точку |
| 3. Своё дочернее окно с учётом масштаба (смешанный DPI) и свой swap chain | 0 % | 3 точки | точка в точку |

Выводы:
- Достаточно варианта 2: swap chain с буферами в настоящих точках окна, на самом окне игры. Дочернее окно и смена
  DPI-режима процесса не нужны, координаты Windows для игры не меняются.
- Настоящий размер клиентской области — `GetClientRect` внутри `SetThreadDpiAwarenessContext(PER_MONITOR_AWARE_V2)`
  (функция берётся через `GetProcAddress`; без неё — размер для Windows, как в 0.2.0).
- `GetDpiForMonitor` программе без DPI-режима всегда отвечает 96 — для расчёта не годится.

## 3. Величины

- `L` — разрешение игры: её back buffer (в окне — клиентская область при запуске, на полном экране — `SetDisplayMode`).
- `O` — вывод: клиентская область окна в настоящих точках (§2).
- Картинка `P = fitPicture(L, O)` — наибольший прямоугольник с пропорциями `L` внутри `O`, по центру, на целых точках
  (уже есть с этапа 1). Масштаб `s = P / L` (по ограничивающей оси, у пользователя 3360 / 1920 = 1,75).
- Масштаб рендера `r = render_scale / 100`, 1,0–2,0 (суперсэмплинг).
- Множитель `k = s · r`; внутренний кадр (RT и глубина) `R = round(L · k)` — в целых числах, с тем же округлением, что
  у `P`: при `r = 1` `R = P` и вывод — точка в точку. (С плавающей точкой `L · k = x,5` округлялось бы иначе: 640×480 в
  окне 646×485 — кадр 646×484 при картинке 646×485. `round(P · r)` при `r > 1` может выйти на точку за край, который
  покрывают вершины `x · k + 0.5`.) Показ переводит прямоугольник игры в точки кадра по каждой оси отдельно (`R / L`):
  весь кадр игры — ровно весь `R`.
- До первого показанного кадра `k = 1`, `R = L`: стартовая калибровка видит ровно картинку DX7 (§4.3 спецификации).
- `high_resolution = 0`: всегда `k = 1`, swap chain в размере окна для Windows — поведение 0.2.0.

## 4. Рисование при `k`

- **Вершины:** `x' = x · k + 0.5`, `y' = y · k + 0.5` в точках внутреннего кадра (центры точек D3D12 — на половинках);
  `z` и `rhw` не меняются. *Отличие от §4.2 спецификации* (там `(x + 0.5) · k`): та формула при `s ≠ 1` сдвигает картинку
  на полточки игры и оставляет по левому и верхнему краю непокрытую полосу в одну точку. Новая формула покрывает ровно те
  точки, что идеальное увеличение кадра игры; при `k = 1` обе совпадают с этапом 1. Цена: выборка текстур сдвинута
  относительно идеального увеличения на `0.5 − 0.5 / k` точки игры (≤ 0,25 при `k ≤ 2`) — допустимо.
- **Прямоугольники** (viewport, scissor, Clear, Blt в RT) в точках игры `[x0, x1)` переводятся в `[ceil(x0·k), ceil(x1·k))`
  — те же точки, что покрывает квад с такими краями.
- **Показ:** `R` выводится в `P` внутри swap chain размера `O`, вне `P` — чёрные поля. При `R = P` — копия точка в точку;
  при `r > 1` — уменьшение с усреднением по площади (суперсэмплинг).
- **Переход на `k` при первом показе** и **смена `O`** (размер окна, переезд на монитор с другим масштабом): `k`
  пересчитывается, RT и глубина создаются заново, старое содержимое растягивается в новый RT (back buffer должен
  сохраняться после показа), swap chain меняет размер.

## 5. Чтение и запись кадра игрой (уточнение §4.3)

Игра видит кадр размера `L`; наш RT — размера `R`.
- **Чтение** (Blt RT → память, Lock с касанием памяти, GetDC): RT уменьшается на GPU до `L` усреднением по площади во
  вспомогательную текстуру `L`, она читается назад. Ежекадровый Lock без касания — без работы GPU, как сейчас.
- **Запись** (Unlock после записи, Blt память → RT, ReleaseDC): точки `L` загружаются во вспомогательную текстуру и
  растягиваются (билинейно) в прямоугольник RT, переведённый по §4.
- Следствия: скриншоты — размера `L`, как сейчас (подпись с датой пишется обратно растянутой, но этот кадр не
  показывается); затемнение при смене режима (~0,25 с), эффект «волны» и видео Bink мягче на время эффекта;
  калибровка при `k = 1` без изменений.

## 6. Интерфейс

- Интерфейс — всё, что рисуется после первого `SetRenderState(ZENABLE, 0)` после `BeginScene` (§2 спецификации, L11851);
  `BeginScene` сбрасывает признак. Признак `ui` — часть состояния рисования (`DrawSetup`).
- `ui_filter = sharp` (по умолчанию): для квадов интерфейса шейдер выбирает текстуру «чётким билинейным» способом —
  каждая точка картинки становится чётким квадратиком с плавным переходом шириной в одну точку экрана. Увеличение берётся
  из производных текстурных координат по экрану, поэтому подходит и для картинок, которые игра сама растягивает; без
  увеличения (≤ 1) выборка обычная.
- `ui_filter = smooth`: обычная билинейная выборка (мягко, как в 0.2.0 при растяжении Windows).
- Текст — картинка интерфейса, тот же фильтр; чёткий текст в 4K — этап 6. Спрайты мира — без изменений (билинейно).

## 7. Настройки (`uaro-graphics.ini`)

```ini
[display]
mode = auto               ; auto | window | borderless (этап 1B)
high_resolution = 1       ; 1 = рисовать в настоящих точках окна; 0 = как 0.2.0
ui_filter = sharp         ; sharp | smooth

[quality]
render_scale = 100        ; 100–200, %
```

Лог при каждом пересчёте: «игра LxL, вывод OxO, s, r, k, кадр RxR, картинка WxH в x,y».

## 8. Проверка

- **Linux, ядро:** расчёт `s`, `k`, `R`, `P` (окно 1920×1080 при 175 %, полный экран 4K, `r = 1,5`, 100 %, без API);
  перевод прямоугольников; эталонный растеризатор при `k = 1,75`: полноэкранный квад покрывает все точки `R` без полос,
  квад шириной в точку игры — `k` точек, при `k = 1` — совпадение с этапом 1; признак интерфейса (`BeginScene`,
  `ZENABLE`); математика `sharp` (центры текселей точные, переход в одну точку, та же формула, что в HLSL); ключи ini.
- **Windows:** сборка без предупреждений, `check_dll`, финальное ревью; чек-лист 0.3.0 у пользователя: чёткость мира,
  интерфейс в `sharp` и `smooth`, скриншот 1920×1080, затемнение, курсор, ROExt и геймпад, `high_resolution = 0`.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Элементы интерфейса из соседних квадов дадут швы при нецелом `k` | одна формула для всех вершин: общие края совпадают; проверка у пользователя |
| Текст в `sharp` угловатый | `smooth` как выбор; чёткий текст — этап 6 |
| «Волна» и затемнение медленнее и мягче | редкие эффекты; уменьшение и увеличение на GPU |
| Окно переезжает на монитор с другим масштабом | пересчёт `k` на каждом показе |
| Чтение кадра при масштабе медленнее | только при реальном касании памяти, как сейчас |
